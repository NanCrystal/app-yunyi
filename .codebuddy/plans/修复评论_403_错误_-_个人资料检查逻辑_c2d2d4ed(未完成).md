## 产品概述

修复小程序用户在调用 `POST /comments` 接口时被 403 拒绝的问题。用户已完善个人资料（前端显示 `isProfileComplete: true`），但后端仍因数据库中 nickName/avatarUrl 为空而拒绝留言请求。

## 核心功能

- 修复后端登录接口丢失用户资料数据的问题：前端在 `loginWithNewProfile()` 中将 `{ nickName, avatarUrl }` 随登录 code 一起发送，但后端 `LoginDto` 仅接收 `code` 字段，profile 数据被完全丢弃
- 实现头像持久化：用户通过 `chooseAvatar` 获得的 `wxfile://tmp_...` 临时路径需要先上传至七牛云获取永久 URL，再保存到数据库
- 确保评论创建时的资料校验能正确通过：数据库中 nickName 和 avatarUrl 均非空

## 问题根因链路

1. 前端 `auth.ts:395-399` 发送 `{ code, profile: { nickName, avatarUrl } }` 到 `/mp-auth/login`
2. 后端 `login.dto.ts` 只有 `code` 字段 → **profile 数据被 NestJS ValidationPipe 静默丢弃**
3. 后端 `mp-auth.service.ts:65-83` 登录逻辑只做 code2session + 查找/创建用户，**从不保存 nickName/avatarUrl**
4. 数据库 MpUser 表的 nickName/avatarUrl 为 NULL → `comment.service.ts:29` 抛出 403

## 技术栈

- **后端框架**：NestJS + TypeScript + Prisma (SQLite)
- **文件存储**：七牛云 Qiniu（项目已有基础设施）
- **文件上传**：Multer + diskStorage（已有 UploadController 模式）
- **前端**：微信小程序原生开发 + TypeScript
- **认证方式**：JWT Bearer Token（MpAuthGuard）

## 实现方案

采用「**头像预上传 + 登录携带永久URL**」策略，分三层修复：

### 第一层：后端登录接口接受并保存资料数据

修改 `LoginDto` 增加 optional 的 `profile` 嵌套对象；在 `MpAuthService.login()` 中，当 profile 存在时对用户记录执行 upsert 更新 nickName 和 avatarUrl。这确保了即使不走头像上传流程，直接传入网络 URL 的场景也能工作。

### 第二层：前端头像预上传至七牛云

在 `loginWithNewProfile()` 中，调用 login API 前，先用 `wx.uploadFile` 将临时头像上传到已有的 `POST /upload/image` 端点（30MB 限制，返回七牛云永久 URL）。获得永久 URL 后，将其随 profile 一起发给登录接口。

### 第三层：复用现有上传接口无需改动后端上传模块

`POST /upload/image` 已支持图片上传到七牛云并返回 `{ url: "/uploads/..." }`，前端拼接 CDN 域名即可得到完整 URL。该接口无需鉴权（skipAuth），适合登录前调用。

## 关键实现细节

- **LoginDto 扩展**：新增可选字段 `profile?: { nickName?: string; avatarUrl?: string }`，不破坏现有纯 code 登录的兼容性
- **login() 方法改造**：在 findOrCreate 用户之后、签发 JWT 之前，判断 if(dto.profile?.nickName || dto.profile?.avatarUrl) 则执行 prisma.mpUser.update 保存资料
- **前端上传时机**：在 `loginWithNewProfile()` 第2步（调 login API）之前插入上传步骤，用 Promise 链保证顺序执行
- **错误处理**：头像上传失败时降级为仅传昵称（avatarUrl 为空），用户后续可通过 updateProfile 补充头像
- **CDN 域名拼接**：从环境变量 `QINIU_DOMAIN` 获取或使用默认域名，前端也可硬编码已知的 CDN 域名

## 注意事项

- **向后兼容**：`profile` 字段为可选，纯 code 静默登录不受影响
- **幂等性**：重复登录带相同 profile 时 update 是幂等的
- **性能影响**：仅在带资料登录时多一次 DB write，无额外查询开销
- **安全考虑**：`/upload/image` 无需加鉴权（登录前必须可访问）；profile 数据来自客户端信任度低，但 nickName/avatarUrl 本身就是用户提供的信息，无安全风险
